## Existing playback path

- Rust's shared decoder converts supported WAV/FLAC/MP3 inputs to canonical 48 kHz stereo PCM16. Each decoder starts its sample index at zero and uses bounded decoded queues.
- Desktop staging and its `SelectedSourceRegistry` retain one selected source. `start_playback` creates one decoder and one packetizer; packetizer EOF pads a short packet with silence and completes the stream. The playback pump sends `Stop` and tears down the monitor at EOF.
- Android stages selected content URIs into bounded app-private files, validates them through the shared Rust decoder, then streams an ordered playlist through one Rust packetizer and host monitor runtime.
- `StreamStart` identifies one stream and format and now carries optional current queue-entry identity/display metadata. Audio datagrams carry sequence and first-sample index. Restarting a stream reinitializes listener playback state. The newly added `TrackBoundary` preserves the stream and names a sample index; strict frame-version validation rejects mixed protocol versions.
- Desktop playlist playback keeps one packetizer, stream ID, sequence timeline, and monitor alive across track boundaries. Android listener presentation follows the sample-indexed event without resetting the sink. Android host still decodes and sends one track at a time, and final stream teardown is immediate at natural EOF; those paths are not gapless yet.

## Candidate timeline design

Use one `StreamStart` and one `stream_id` for a continuous play session. Keep packet sequence and sample indices monotonic across tracks. Normalize each source through the shared decoder, then feed adjacent canonical PCM into a single packetizer without marking intermediate track EOF as stream EOF or padding at track boundaries. Use a bounded current/next decoder pipeline so the next source is opened and prebuffered before the current decoder reaches its exact end. Emit a track-boundary event carrying the new queue-entry identity, display metadata, and effective sample index; listeners apply it against their existing sample clock while retaining the same scheduler, render ring, and output device. `Stop` is reserved for explicit Stop or final queue exhaustion.

Version negotiation is strict equality at the frame header, so mixed-version peers fail visibly before playback rather than claiming support for the new queue transition. Queue revisions and source capabilities stay in bounded control-plane state; paths and Android URIs remain platform-owned.

Protocol v3 defines `StreamStart` optional current-entry identity/display fields and `TrackBoundary` with the existing session and stream IDs, exact first sample index of the next track, an opaque queue-entry ID, and bounded display metadata. Control transport validation accepts the boundary only host-to-listener. Protocol version 2 remains rejected by strict frame version validation, and discovery advertises version 3. Desktop and Android open the next decoder while the current track runs, feed adjacent canonical PCM through one packetizer and sequence timeline, and emit the boundary before the next track's first packet. The desktop pump sends the control ahead and applies the host queue transition at the sample's scheduled transport time; Android broadcasts the boundary before pulling the following audio frame and applies its host transition at the scheduled host-clock deadline. Android host transport can also target current-stream metadata and pending boundaries to one approved listener; the approval path sends this state without restarting existing listeners and re-announces outstanding boundaries on resume. A socket-level test verifies targeted `StreamStart` and `TrackBoundary` delivery. Android end-to-end listener timing/reconnect coverage remains open. The packetizer cancellation path cancels the active decoder before joining it, so stopping does not strand a decoder blocked on its bounded output queue. Android listeners retain the listener runtime and schedule current-track title changes from the boundary sample index and accepted host-clock offset; pause and resume cancel/recalculate pending presentation timers against the re-anchored stream. Remaining work includes dynamic retargeting after edits, end-to-end late join/reconnect qualification, late decoder-read recovery, and measured device-level output continuity.

The scheduler and jitter buffer accept a configured `first_sequence` for initialization at a later point on the existing sequence-zero host timeline; defaults preserve fresh-stream behavior. Core tests verify a join beginning at sequence 5 is scheduled at the sequence-zero anchor plus 100 ms. The active Android listener path currently uses the existing far-future bootstrap, which is covered by a core test joining at sequence 500; targeted controls now supply the current track identity and pending boundary. The new `first_sequence` option is a lower-level initialization capability, not yet carried in the protocol.

## Bounds to validate before committing API limits

- Existing shared decoder hard limits: 8 GiB per source, 48 kHz stereo canonical output, 960-frame chunks, 8 default queued chunks (160 ms), up to 64 chunks (1.28 s). The Rust playlist now caps at 100 entries and 16 GiB of unique source sizes; entries sharing one source ID count its bytes once. A source with unknown byte length is budgeted at the decoder maximum.
- Existing desktop packetizer worker has a bounded packet queue and the broadcast path uses a 1,000 ms send-ahead horizon. Rust queue limits are 100 entries and 16 GiB of unique source bytes. Desktop currently opens at most the current and next decoder; the worker's immutable upcoming list and lack of a prebuffer readiness snapshot remain open.

## 2026-10-16 desktop terminal-event precedence correction

The desktop sender's bounded packetizer can finish ahead of network delivery. Previously, `run_pump` treated `packetizer.cancel_and_join().is_ok()` as authoritative natural EOF **even when a boundary broadcast, actor scheduling, or another transport step had failed**. A concurrent explicit Stop after the packetizer finished could also emit `EndOfStream` and advance the queue instead of preserving its current entry. The pump now selects terminal actor events by actual outcome: transport/worker failure → `AudioEvent::Failed`; otherwise explicit Stop → `Stopped`; otherwise completed packetizer → `EndOfStream`. Five deterministic tests cover both race orderings, genuine exhaustion, and cancellation. This is a safety correction, **not** the unresolved Rust boundary-commit decision or physical gapless acceptance. Exact-head Rust/Tauri qualification remains required.

## 2026-10-16 — Host actor rejects unannounced boundary application

The host actor now requires a corresponding `TrackBoundaryScheduled` reservation with matching entry ID and sample index before accepting `TrackBoundaryApplied`. Previously, if no reservation existed it still accepted an application whenever the upcoming entry ID matched. That allowed stale control delivery to advance the queue after a legal edit or after Stop/replay. New deterministic actor regressions cover both cases, verify queue revision/current-entry preservation on rejection, and check that an exact scheduled boundary still applies.

**Scope:** This is an actor-side fail-closed guard, not a full fix for the packetizer output queue's earlier commit point. The existing worker can still enqueue a boundary before the sender announces it to the actor; host queue edits accepted in that interval can still conflict with already-buffered audio. Keep TODO §3's retargeting race open until the worker and actor coordinate boundary commitment atomically and production Android/desktop tests prove the full path. Rust/Android/desktop exact-head qualification remains pending until an executable test environment and CI are available.

## 2026-10-16 — EOF-to-promotion retarget safety (partial)

The shared playlist worker now performs one additional latest-value upcoming-queue check **after** the outgoing decoder completes but **before** promoting the already-prefetched successor. A queue edit accepted while the outgoing track's last chunk is draining under bounded backpressure can therefore cancel the stale staged decoder and choose the replacement before constructing the successor boundary. If the edit removes the last successor too late to mark the outgoing chunk as final, the worker now flushes the retained partial PCM packet with an empty final chunk, without introducing extra source samples (see commit `013b2e1`). A bounded-output regression covers removing the successor during backpressure without emitting its boundary.

This closes one race window, not the producer-to-consumer boundary-commit race. Once the worker has enqueued a boundary, later accepted edits can still conflict with that already-buffered track. The separate producer-commit protocol note specifies the required actor-serialized reservation and deterministic interleavings. The Android FFI and desktop host paths still need that coordinated commit/retarget implementation. No physical or exact-head CI acceptance is claimed from this change.

## 2026-10-16 — Direct packetizer queue-entry bound enforcement

The Rust actor already limits the authoritative host queue to 100 entries with unique IDs. Direct streaming packetizer and UniFFI callers previously bypassed those checks: `spawn_playlist` accepted arbitrarily many upcoming factories and duplicate entry IDs, and `replace_upcoming` could enqueue an oversized/duplicate live replacement. Both paths now reject duplicate upcoming IDs and reserve one current-track slot within the existing 100-entry limit. A direct FFI regression exercises oversized initial playlists, duplicate initial IDs, oversized live updates, and duplicate live updates. This is defensive input validation; it does **not** resolve the producer/actor boundary-commit race or qualify physical gapless playback.

## 2026-10-16 — Live updater current-entry identity validation

Direct packetizer/UniFFI live updates previously checked duplicate IDs only *within* the upcoming list, not against the active track. The shared updater now tracks current identity under the same lock as pending edits, rejects duplicate-current IDs before accepting an update, and revalidates at consumption. Promotion updates the identity and removes the just-promoted entry from an already-accepted pending edit, preserving the remaining order rather than replaying the same song. Core, promotion-state, and UniFFI regressions cover these cases.

**Scope:** This closes a direct-updater identity bypass, **not** the producer/actor boundary-commit race. An already-enqueued boundary can still conflict with an actor-accepted queue edit; the producer-side reservation protocol and physical playback qualification remain open.

### Direct packetizer entry-ID validation

The direct playlist factory now also enforces the authoritative queue's 128-byte entry-ID limit, no leading/trailing whitespace, and no control characters. This prevents direct core/UniFFI callers from bypassing queue ID validation even before playback starts. A core regression exercises oversized, whitespace-padded, and control-character IDs. This is distinct from the still-open boundary reservation race.

## 2026-10-16 — UniFFI live-updater terminal-state guard

The Android-facing `FfiHostPlaylistStreamer` now records an atomic terminal flag on explicit cancellation and after the worker output disconnects. `replace_upcoming` rejects updates to an observed closed stream with `FfiHostPlaylistError::Closed` instead of silently reporting success for a stream that cannot consume the edit. Existing FFI fixture tests now cover cancellation and natural EOF. This is a lifecycle safety guard, not a solution to the producer/actor boundary reservation race: a concurrent close can still race an already-started update, and production boundary commitment remains open in TODO §3. The new regressions await an executable exact-head Rust gate.

## 2026-10-16 — Preserve a valid next-track prebuffer across non-target queue edits

The shared packetizer's `refresh_pending_playlist_update` previously cancelled and reopened the prepared next decoder on **every** accepted upcoming-list update, even when the next entry and display identity remained unchanged. An append or reorder confined to tracks after that entry could therefore discard already-decoded PCM just before a gapless boundary, add decoder startup latency, or trigger a new file-read failure despite having a usable prebuffer. The worker now retains the successfully opened next decoder when the revised upcoming list begins with that same entry and display identity, consumes that head from the new pending list, and only reopens if the target changes or the existing decoder failed. A unit regression covers the identity policy.

This is a prebuffer-continuity improvement, not an atomic producer/actor reservation. Already-enqueued successor frames can still conflict with an actor-accepted edit, and the §3 checkbox remains open. Exact-head Rust tests and physical output qualification remain required.

## 2026-10-16 — Reject late natural EOF after Stop or failure

The actor now accepts `AudioEvent::EndOfStream` only while playback is `Playing`. A delayed EOF delivered after explicit Stop or a retryable audio failure previously cleared the authoritative queue and source alias, making Stop/replay and Retry inconsistent. Two actor regressions assert the queue revision, current entry, and playback state are unchanged when such a delayed event is rejected. The pre-existing playing-state natural-end test continues to assert queue exhaustion and session retention. This guard does not solve a stale EOF from a previous stream arriving *while a new stream is Playing*, because `AudioEvent::EndOfStream` currently has no compared active-stream identity. Keep §4/§9 qualification open until stream generations and physical paths are exercised.

## 2026-10-16 — Producer-terminal playlist updates fail closed

The shared Rust playlist worker now marks its updater terminal when it exits (natural EOF, cancellation, decoder error, or unwind) under the same mutex used by `replace_upcoming`. This prevents a direct core or desktop caller from receiving a false success for an update after the producer has exited, even while buffered output remains unread. The UniFFI adapter maps the terminal rejection to its existing typed `Closed` error. Core regressions cover natural completion before consumer observation and cancellation. This is a lifecycle safety improvement, **not** a producer/actor boundary reservation: edits accepted by the actor before the worker's terminal transition may still race an already-enqueued boundary. New tests remain unqualified while exact-head CI is unavailable.

## 2026-10-16 — Final direct-updater promotion race guard

The playlist worker now checks for an accepted upcoming-list edit and commits the next current-entry identity under the same mutex as `replace_upcoming`. If an edit wins after the final EOF refresh, the worker consumes it, retargets the prepared decoder, and retries instead of silently filtering the edited successor during promotion. A core regression verifies that a removed successor cannot be promoted when a replacement edit is pending. This addresses the **direct packetizer updater** race only; it does not establish an authoritative actor/producer boundary reservation before successor frames enter the bounded output queue. Keep TODO §3 unchecked. CI at the new master head still needs an executable Rust job; physical gapless playback remains unqualified.

## 2026-10-16 — Reject stale progress and EOF after replay has begun

The actor now binds a private active stream ID on the first accepted `PositionAdvanced` event of a playback generation. Later progress and natural EOF from a different stream are rejected without changing the queue or playhead. Stop, fresh Play, failure, and host/listener teardown reset the binding; pause/resume retains it. Two actor regressions cover a delayed old EOF after new-stream progress and a mismatched position update. This is deliberately a **partial** generation fence: if an old event arrives before the new stream's first position, it can still be accepted. A production stream-start identity handshake is needed to close that window. It does not implement the producer/actor boundary reservation required by TODO §3; CI and physical acceptance remain open.

## 2026-10-16 — Fence the last stopped stream before replay progress

The actor now remembers the most recently retired stream identity when Stop, failure, natural EOF, premature EOF, or session teardown retires an active stream. During the next playback generation, stale position and EOF events from that retired stream are rejected even **before** the new stream reports its first position; the previous active-ID check only began protecting after new progress. A regression tests the Stop → Play → old progress/EOF → new progress/EOF interleaving and a second verifies pause/resume keeps the active stream. This remains a partial fence: a stream that never reported position cannot be retired by identity, and more than one older stream is not tracked. A production stream-start handshake is still required for complete generation identity and for producer-side boundary reservation. Exact-head executed tests and physical qualification remain open.

## 2026-10-16 — Multiple retired stream generations (partial)

The actor now retains a bounded FIFO of up to 16 distinct retired stream IDs instead of only the latest. Delayed position or EOF from two or more earlier Stop/Play generations cannot claim the new stream before its first progress event. Both host-session and listener-connection teardown use the shared retirement helper. New Rust actor regressions cover two stopped generations and the history bound. This remains a partial safeguard: streams that never emitted progress cannot be retired by identity, and IDs evicted from the bounded history are no longer fenced. A production StreamStart handshake, producer/actor boundary reservation, executed exact-head CI, and physical gapless acceptance remain outstanding. Do not close the corresponding TODO items from this change alone.
